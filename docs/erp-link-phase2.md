# 사고종결 ERP 자동결재 2단계 — 격리 스테이징 개발 결과

검증일: 2026-10-08. 기준 main: `805b100c76f1a7c1efb8e966047a1e293e273596` (4.4.44).

**실제 ERP 자동연동은 아직 구현/검증되지 않았다.** 허용된 연동 계약과 별도 ERP 시험 계정이 없어, 외부 ERP 어댑터는 `erp_integration_not_authorized`로 차단했다. 이번 변경은 실제 Supabase 스테이징에 배포한 가상 자료 전용 결재 서비스와 재사용 가능한 결재 패널이다. 운영 앱 화면/종결 경로에는 아직 삽입하지 않았다. 이 PR은 운영 병합 준비 상태가 아니다.

## ERP에서 확인한 사실과 한계

사용자가 직접 로그인한 클라우드 브라우저로 전자결재와 인사관리 UI를 읽기 전용 확인했다. 계정/비밀번호/쿠키/세션/네트워크 인증값을 추출하거나 코드에 보관하지 않았다. 비공식 내부 요청을 재현하지 않았다.

| 기능 | 운영 ERP 화면 관찰 | 이번 실제 자동연동 검증 |
|---|---|---|
| 기안 | 기타품의/승인요청서 `template_id=4`; 문서제목, 제목, 세부내역, 에디터 | 화면 존재만 확인. 자동 생성/저장 미실행 |
| 첨부 | PDF, DOCX, XLSX, JPG, PNG, ZIP, RAR, HWP, HWPX 선택 UI | 업로드/용량 제한/바이러스 검사 미확인 |
| 결재선 | 저장된 결재선, 직접 지정, 조직별 사용자 목록 | 아무 결재자도 선택/저장하지 않음. 사고종결용 승인된 결재선 미확정 |
| 상신 | 임시저장/상신 버튼 존재 | 실제 상신/알림 발송 미실행 |
| 결과 조회 | 결재함에 문서번호 및 진행/반려 상태가 표시됨 | 외부 조회 API/웹훅 미확인. `처리완료`만으로 승인 판정 불가 |
| 인사 | 부서/팀/직책/연락처 목록 | 안정적인 사번, 재직 여부, 외부 조회 권한 미확인. 실명/연락처를 저장하지 않음 |
| 외부 연결 설정 | 관리자 화면에 “권한이 필요합니다. 관리자에게 권한 요청을 해주세요.” | 현재 계정으로 API/연동 설정 확인 불가 |

공개 검색에서도 공식 API 문서를 찾지 못했다. 이는 API가 없다는 증거가 아니다. 관리자/ERP 공급사의 공식 문서와 허용 범위를 받아야 한다. 브라우저로 입력 가능한 UI 요소는 보이지만, 실제 입력·업로드·상신 테스트는 수행하지 않았으므로 RPA 성공을 보장할 수 없다. RPA를 선택해도 독립 실행 환경, 허용된 서비스 계정, MFA/세션 만료 정책, 화면 변경 대응, 결과 재조회 및 장애 복구가 필요하다. 현재 ChatGPT 클라우드 브라우저 세션은 상시 연동 수단으로 채택하지 않는다.

## 기존 흐름 및 PR #51 판단

기존 흐름은 최초 사고 접수 승인 → 안전관리자 재발방지계획 → 현장 조치/증빙 제출 → 안전관리자 확인이다. `corrective.status=approved`가 되면 현재 클라이언트와 서버가 사고를 자동 종결한다.

| 파일/개발본 | 판단 |
|---|---|
| `workflow-lifecycle-v413.js` | 조치 승인 시 `closed`로 변경. 향후 ERP 대상 사고는 이 자동종결을 서버의 ERP 승인 판정으로 대체해야 함 |
| `edge-functions/enl-incident-sync-v411/index.ts` | `normalizeLifecycle` 및 push 경로에 자동종결이 각각 있음. 두 지점과 동시성/무결성 해시/공식기록 처리를 함께 수정해야 함 |
| `workflow-prevention-v429.js` | 계획·현장조치·확인 기능을 유지. 반려는 기존 corrective 보완요청과 연결해야 함 |
| `management-approval-v448.js` | 기존 최초 사고보고 본사 확인결재를 ERP 최종 종결결재와 구별해야 함. 이번 변경에서 제거하지 않음 |
| PR #51 | 병합하지 않음. 이미 종결된 사고의 ERP 문서번호/상태 수동등록 방식은 최종 목표와 다름 |
| phase1 재사용 | 안전관리자 제한, 과거사고 제외, 개인정보 없는 제목, 화면 관찰/양식 매핑, 기본 비활성화 원칙 |
| phase1 수정/폐기 대상 | 선종결 후 수동 ERP 등록, 사용자가 선택한 ERP 승인상태를 종결 근거로 쓰는 방식, 수동 문서번호를 유일한 연결키로 쓰는 방식 |

이 변경은 main을 기준으로 **새 파일만 추가**한다. 기존 앱 코드, 서비스워커, 배포 HTML, 기존 DB 테이블/함수/트리거와 알림 설정은 변경하지 않는다. 따라서 기존 기능을 대체하거나 회귀 검증을 완료한 것으로 보고하지 않는다.

## 구현한 범위

- `erp-close-v2/core.mjs`: 최초 승인·조치 확인·계획·증빙 선행조건, template 4 기안 패키지, 실제 DOCX 바이트 생성, 첨부 SHA-256 및 불변 snapshot.
- `panel.mjs`, `staging.html`: 안전관리자용 **ERP 사고종결 결재 요청**, 진행상태 표시/새로고침, 실패 시 재시도. 권한은 서버에서 재검증한다. UI의 역할 선택은 권한 부여가 아니다.
- `enl-erp-close-v2-staging`: 별도 private schema에 가상 사고·작업·모의 ERP 문서·감사로그를 저장한다. 실제 운영 사고 ID/본문을 받는 import/update 기능은 없다.
- DB 행 잠금과 `(case_id, revision)`/`client_reference` 유일키로 중복 요청 방지.
- 내구성 있는 작업 상태, worker lease와 만료 후 회수, 재시도 시각, 오류 기록. 모의 ERP 문서 생성과 앱 반영을 다른 트랜잭션으로 처리하여 응답 유실을 재현한다.
- 모의 결재선은 `qa-manager`, `qa-executive`뿐이다. 실제 승인된 결재선이 아니다.
- 모든 첨부 바이트의 해시를 검증한 뒤 모의 상신. 응답 유실 시 동일 외부참조의 기존 문서를 재조회해 중복 생성하지 않는다.
- 제공자 결과의 문서 ID, 외부참조, snapshot hash를 검증. 명시적 승인만 `closed`; 반려는 `corrective.status=rejected`, 사고 최초 승인 유지. 알 수 없는 결과와 조회 실패는 미종결 유지.
- 반려 후 가상 보완·재확인으로 revision을 올리면 새 작업 생성. 이전 작업/증빙/감사로그 보존. 실제 현장 재확인 연동은 아직 없음.
- `worker.mjs`: 브라우저 없이 due 작업을 처리하는 스테이징 실행기. 스테이징 실행은 검증했지만 상시 스케줄러는 설치하지 않았다. 실제 `--once` 실행으로 due 작업 5건을 처리해 모두 pending 상태를 확인했다.

일반 상태 전이는 `queued → submitting → pending → approved/rejected`다. 장애 시 `retry_wait/submission_unknown/status_unknown/error`로 남는다. 미확정 상태에서 임의 종결/내용 갱신은 서버에서 거절한다. 이 보호는 **이번 격리 서비스에 적용**되며, 기존 앱의 운영 저장 경로는 아직 그대로다.

## 배포 및 검증

- 스테이징 프로젝트: `enl-incident-staging` (`zgwxzfvvpqgdedyobwmg`).
- 전용 함수: `enl-erp-close-v2-staging` v3, `provider=mock`, `liveERP=false`.
- 전용 스키마: `enl_erp_close_v2`; public 사고자료/사용자/알림과 연결되는 트리거 없음.
- 프로젝트 호스트 allowlist로 다른 프로젝트 실행 차단. 실제 ERP URL을 호출하는 코드 없음.
- JWT 게이트는 끄고 함수 본문에서 랜덤 256-bit 단기 시험 토큰의 SHA-256, 만료, run scope, 역할을 검사한다. 토큰은 ERP 인증정보가 아니며, raw token은 repo/앱 저장소/로그에 저장하지 않는다. 이번 검증에 발급한 시험 토큰은 검증 종료 후 만료 처리한다.
- 신규 5개 테이블 RLS ON, anon/authenticated 접근 권한 없음. 보안 advisor에는 의도적인 RLS 무정책(INFO)만 보고됨. [Supabase 설명](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy).

| 실제 스테이징 HTTP 시나리오 | 11/11 통과 |
| 신규 사고에 8개 동시 요청 | 새 작업 1개, 중복 반환 7개 |

| 모의 승인/반려 및 중복 결과 | 승인만 종결, 반려 보완요청, 중복 결과 무해 |
| 전송 전 장애/상신 후 응답 유실/첨부 실패 | 오류 기록 후 재시도 성공, 중복 문서 없음 |
| 잘못된 역할/만료 토큰/다른 시험 run | 거절 |
| 첨부 파일 | 실제 OOXML ZIP/XML 및 SHA-256 검증 |
| 클라우드 브라우저 UI | 로컬 미리보기 연결 거절로 시각/E2E 검증 미완료 |
| 실제 ERP E2E | 미실행, 승인된 연동 계약/시험환경 없음 |

첫 배포에서 postgres JSON 파라미터의 이중 인코딩을 발견해 `sql.json/tx.json`으로 수정했고 DB JSON object 제약을 추가했다. 이후 스테이징 테스트를 다시 실행해 통과했다. `sql/erp-close-v2-staging.sql`은 최종 상태의 새 스테이징 부트스트랩이며 이미 적용한 schema에 재실행하지 않는다.

기존 스테이징 테이블 건수는 전후 동일: 사고 15, 사고 감사 69, push event 4, push delivery 0, 본사 사용자 5. 이는 건수 확인이며 전체 자료 내용 비교를 의미하지 않는다. 구현 및 테스트는 전용 스키마에만 썼고 운영 DB에는 쓰기를 수행하지 않았다.

검증 원본은 `tests/erp-close-v2/results/`에 가상 ID와 결과만 남긴다. 실 ERP 화면/인명/사고자료/인증값은 포함하지 않는다. 기존 CI 일부가 운영 API를 호출하므로 `[skip ci]`로 이 개발 커밋의 자동 CI를 중지하고 로컬 및 전용 스테이징 결과를 별도로 기록한다. GitHub CI 통과라고 보고하지 않는다.

## 재현

1. 로컬: `node --test tests/erp-close-v2/core.test.mjs tests/erp-close-v2/panel.test.mjs tests/erp-close-v2/worker.test.mjs`.
2. 전용 테스트 디렉터리를 repo 밖에 지정해 `node tests/erp-close-v2/provision-test.mjs /private/qa-directory` 실행. 권한 있는 스테이징 DB 운영자가 생성된 `hashes.sql`만 적용한다. raw token을 GitHub/메시지에 붙이지 않는다.
3. `ERP_V2_TEST_CREDENTIALS=/private/qa-directory/credentials.json node tests/erp-close-v2/staging.test.mjs` 및 `concurrency.test.mjs` 실행. endpoint는 스테이징으로 고정돼 있다.
4. `ERP_V2_TEST_CREDENTIALS=/private/qa-directory/credentials.json node erp-close-v2/worker.mjs --once`로 작업 처리. 상시 시험 실행은 `--once` 생략. 인증이 만료되면 실행기는 종료한다.
5. `python -m http.server 4173` 후 `http://localhost:4173/erp-close-v2/staging.html`에서 가상 사고 ID와 해당 run의 safety 시험 토큰으로 연결. ERP 비밀번호를 사용하지 않는다. 운영 계정을 이용한 실제 앱 E2E는 지원하지 않는다.

## 운영 적용 전 필요한 것

1. ERP 관리자/공급사의 허용된 API 또는 RPA 연동 승인, 공식 문서 및 별도 시험환경/계정. 외부참조 기준 중복 조회/멱등성, 문서 생성·첨부·상신·조회, 최종 승인/반려 상태의 정확한 계약.
2. template 4 필드키/첨부 제한/순서, 사고종결용 결재선 ID와 활성 사용자 ID, 부재/퇴사/대결 처리, 부서 권한 확정. HR 외부 조회 범위는 최소화.
3. 허용된 서버 간 인증과 비밀 저장소, 최소권한 DB 계정, 사용자 인증 전환/검증, TLS/IP 허용 및 감사/보존 정책. 브라우저 쿠키 복사 방식은 채택하지 않음.
4. 실제 ERP provider 구현 및 공급사 sandbox 계약 테스트. 상신 여부가 불명확하면 외부참조로 재조회하고, 조회 불가능하면 재상신하지 않도록 운영 정책 확정.
5. 운영 앱의 두 자동종결 서버 경로/클라이언트 경로를 ERP 대상 사고에 한해 변경하고, 공식기록 해시/알림/출력/최초 승인/현장조치/기존 본사 확인결재를 함께 회귀 검증. 안전관리자 변경 요청만으로 ERP 승인 상태를 위조할 수 없도록 저장 API/DB 경계까지 보호.
6. 상시 worker 또는 서명 검증 웹훅, 모니터링/재시도 상한/수동 복구, 장애 시 종결 금지, 점진적 전환 대상 및 롤백 절차. 실제 알림은 공급사 시험환경에서만 먼저 검증.

허용된 외부 연동 방식이 끝내 제공되지 않으면 자동 상신은 출시하지 않는다. 그 경우 수동 ERP 결재 후 신뢰 가능한 결과 확인 방식의 별도 범위를 결정해야 한다.
