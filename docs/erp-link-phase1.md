# 이앤엘 사고보고앱 × ERP 연동 1단계 (비운영 개발본)

## 기능 범위
- 사고보고앱의 **안전관리자**만, **사고 최종 종결 + 재발방지조치 승인** 건에서 ERP 연계 패널 이용.
- 기존 사고보고 Excel 다운로드 기능을 그대로 호출. ERP 기안은 사람이 수행하며 자동 업로드하지 않음.
- ERP 화면은 직접 열기만 함. 로그인 정보, 쿠키, AI 브라우저 세션을 수집하거나 ERP 내부 호출을 하지 않음.
- 사용자 확인을 거쳐 ERP 문서번호 및 수기로 확인한 상태를 별도 DB에 기록. **ERP 실시간 확인이 아닌 수기 기록**이라는 점을 표시.
- 이전 ERP 결재 사고를 이관한 과거사고는 신규 연계에서 제외.
- 사고 본문/사진/진단정보/결재선은 연계 DB에 저장하지 않음.
- 동일 사고의 동시편집 충돌은 revision으로 검출, 변경 이력은 별도 감사 테이블에 보존. 서로 다른 사고 간 ERP 문서번호 중복은 현재 차단하지 않음.
- 전체 패널은 기본 비활성화. 기안 준비 기능과 문서번호 조회·저장 기능의 활성화 설정을 분리하여, 화면 검토만으로 운영 서버가 호출되지 않도록 함.

## 환경별 적용
1. GitHub PR/개발 브랜치에서 코드·테스트 검토.
2. 스테이징 DB에 `sql/erp-link-schema-v1.sql`을 적용 (기존 테이블 수정 없음).
3. 기존 개발 서버 함수는 앱 커스텀 계정의 해시 증빙을 재검증하는 방식이다. 운영 활성화 전 세션 인증·해시 노출·재사용 위험을 검토해야 하며, 이 문서를 근거로 운영 JWT 검증을 변경하지 않는다.
4. 실제 ERP 내부 화면·문서 등록/조회 권한 확인 후 동작을 검증.
5. 운영 반영 전 개인정보 처리 범위, ERP 관리자 승인, 권한, 연동 기록, 롤백 경로 확인.
6. 운영 배포 때만 운영 DB에 스키마 적용 + 별도 함수 배포 + GitHub 메인 병합. **현재는 하지 않음.**

## 사용자 시나리오
1. 사고보고앱 → 최종 종결 사고 상세 → [ERP 전달].
2. [Excel 보고서 받기] (진료정보 등 개인정보 포함 가능, 회사 보안절차 준수).
3. [기안 제목 복사] → ERP의 문서제목과 서식 내부 제목에 동일하게 붙여넣기.
4. [세부내역 복사] → [기타품의 양식 열기] → 세부내역(필요시 파일첨부)에 붙여넣고 .xlsx 보고서를 직접 첨부.
5. 결재선·참조자·첨부 내용을 확인한 후 사용자가 직접 상신. 자동 업로드·임시저장·상신하지 않음.
6. 문서번호 저장 기능이 별도 활성화된 경우에만, [ERP 결재함 확인]에서 실제 문서번호와 상태 확인 → [연계 기록 조회] → 수기 등록.
7. 미확인 상태는 승인완료로 표시하지 않음. 임시저장은 상신이 아니며, 반려 문서에도 나타나는 ‘처리완료’를 승인으로 해석하지 않음.

## 제한 및 주의
- API 기반 양방향 동기화, ERP 로그인 통합, ERP 문서 자동 기안/자동승인은 **미구현**.
- 기존 앱의 해시 인증증빙 체계를 그대로 쓰므로 클라이언트 XSS 보호, 계정관리, 서버 접근정책을 우선 준수해야 함. 앞으로 ERP 정식 SSO/API 제공되면 세션형 인증으로 교체 권장.
- 백엔드/DB 기능은 개발 브랜치에 따로 존재하며 운영 DB에 적용하기 전까지 운영 페이지에 표시하면 안 됨.
- 테스트는 가상 사건·계정 기준으로 수행. 운영 실데이터 변경·기안·발송 금지.
- ERP 운영 URL: https://erp.enlife.co.kr/ (전자결재·사원/조직도 화면의 읽기 전용 확인 완료. 저장·상신 기능은 미실행).

## 화면 대조 후 개발본 보완 (2026-10-08)
- 전자결재 `기타품의/승인요청서`의 필수 입력란: 공통 문서제목, 서식 내부 제목, 세부내역. 결재선·참조자·기결재첨부·첨부파일은 사용자가 ERP에서 직접 확인한다.
- 기안 바로가기: `https://erp.enlife.co.kr/gw/eform/documents/new?template_id=4`. 결재함: `https://erp.enlife.co.kr/gw/eform/approvals`.
- 로그인 또는 ERP 변경으로 바로가기가 작동하지 않으면 전자결재 → 기안 작성 → 기타품의/승인요청서를 수동 선택한다.
- ERP 안내에 `.xlsx`가 첨부 허용 형식으로 표시되어 있고 기존 앱 내보내기는 실제 `.xlsx`를 생성한다. 이번 확인은 형식 대조이며, 파일 업로드 성공·용량 제한·결재 진행은 검증하지 않았다.
- 기존 저장 상태는 `submitted`(상신 사실 확인), `approved`(완료 확인) 두 가지뿐이다. 결재대기·진행·반려의 현재 상태 동기화가 아니며, 반려·철회 등을 정확히 기록하는 스키마 확장은 다음 검증 범위다. 초기 선택값을 공란으로 두어 미확인 상태가 자동 지정되지 않게 했다.
- 사원/조직도의 부서·팀·직급은 화면 표기값이다. 이름만으로 계정을 자동 연결하지 않는다. 고유 사원 식별자, 재직상태, 사업장 코드 대응, 권한 부여 기준과 허용된 내보내기/API가 확인될 때까지 인사 동기화·계정 자동생성을 구현하지 않는다.
- 실제 사원 정보, 연락처, 사고 제목·문서번호, 화면 캡처를 이 저장소에 기록하지 않는다.

## 활성화 경계
`erp-link-v1.js` 로드 전에 배포 소유자가 명시적으로 설정해야 한다. 이 개발 PR에는 활성화 설정을 넣지 않는다.

```js
// 가상 데이터가 있는 격리된 검토 화면에서 기안 준비 UI만 확인할 때
window.ENL_ERP_LINK_CONFIG = { enabled: true, registryEnabled: false };
```

- `enabled`가 엄격한 boolean `true`가 아니면 패널·이벤트·인증정보 조회·통신을 모두 시작하지 않는다.
- `registryEnabled`의 기본값은 `false`. 이때 문서번호 조회·저장을 비활성화하고 요청 함수에서도 계정 확인 전에 차단한다.
- 현재 레지스트리 주소는 기존 운영 프로젝트 주소다. `registryEnabled: true`는 운영 서버·권한·마이그레이션·승인이 모두 준비된 배포 때만 사용한다. 스테이징으로 임의 전환해 운영 계정 증빙을 전송하지 않는다.
- UI 활성화 설정은 인증·권한 검사를 대체하지 않는다. 서버의 활성 계정·역할·사고 상태 확인은 계속 필요하다.

## 이번 검증의 범위
- ERP 화면 읽기 전용 조회 및 미입력 양식 열기/닫기. 저장·상신·결재·파일 업로드·인사정보 변경 없음.
- Node 내장 테스트로 요약/제목 민감정보 제외, 종결·역할 제한, 해시 증빙·충돌 처리, 기본 비활성화와 준비 화면의 네트워크 차단을 가상 데이터로 검사한다.
- 운영 DB, 스테이징 DB와 서버 함수는 이번 보완에서 변경하지 않는다. 실제 ERP 자동 연계·Office 실행·iPhone 실기기 확인은 완료로 간주하지 않는다.
- 이번 개발 커밋은 기존 PR 자동 검사 일부가 운영 서버에 요청하는 것을 피하려고 `[skip ci]`로 기록한다. 로컬 무통신 테스트 15개가 통과했다. 병합하지 않으며, 운영 반영 전에는 자동 검사도 운영 쓰기 요청이 없는 격리 환경에서 다시 실행해야 한다.
